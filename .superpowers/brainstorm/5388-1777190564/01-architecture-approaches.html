Compliance Comparison Architecture

How should we process document comparisons in Mizan?

A

Synchronous API (FastAPI endpoint)

Flow: User selects docs → FastAPI makes immediate Claude API calls → streams response back → saves to DB

Pros

  • Simpler implementation (no queue management)
  • Instant feedback to user
  • Real-time progress tracking easier

Cons

  • Long API requests can timeout (50 chunks × multiple calls = minutes)
  • Blocks HTTP connection during processing
  • Poor UX if network drops mid-comparison
  • No retry mechanism
B

Async Celery (existing worker infrastructure)

Flow: User selects docs → API enqueues Celery task → task runs in background → updates DB/Noesia → frontend polls for status

Pros

  • Leverages existing Celery/Redis setup
  • Resilient to timeouts (worker can retry)
  • Scales horizontally (multiple workers)
  • Familiar pattern (matches document processing)
  • Better error handling and monitoring

Cons

  • Slightly more complex (task definition, polling)
  • Frontend needs polling logic
  • Delayed feedback (not instant)
C

Hybrid (Celery + WebSocket streaming)

Flow: User selects docs → API enqueues Celery task → task streams updates via WebSocket → frontend displays real-time progress → saves to DB

Pros

  • Best of both worlds: async resilience + real-time feedback
  • User sees live progress (each chunk comparison)
  • Professional UX
  • Scales well

Cons

  • Most complex (WebSocket, Redis pub/sub)
  • Higher infrastructure cost
  • Requires more frontend complexity
